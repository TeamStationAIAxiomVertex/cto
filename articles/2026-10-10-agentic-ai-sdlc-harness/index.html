Agentic AI SDLC: the harness is now part of the engineering job

An agentic AI SDLC needs a recoverable work loop: clear repo context, bounded tools, useful tests, durable state and an accountable release owner. CTOs and CIOs should fund those pieces together. Buying another coding agent won't settle who owns a failed release.

The interesting shift is where engineering effort goes. Someone still has to define the task, make the system inspectable and decide what counts as done. Agents can write the PR. Your delivery system has to prove the change works, survives a restart and reached the intended environment. That's where things get spicy.

What changed in the agent tool stack?

The integration options are getting more concrete. OpenAI's August 19 Codex platform guide separates bounded, noninteractive jobs through codex exec, programmatic sessions through the SDK, and richer application integrations through app-server. That gives platform teams a practical choice. Match the interface to the work: a CI task needs a different integration from an internal product with resumable threads and approval UI.

Anthropic's April 8 Managed Agents architecture separates the durable session log, the agent loop and the execution sandbox. A replacement harness can read session events and continue. Credentials can stay outside the sandbox. For a CIO, that distinction deserves attention: execution, stored history and access controls have different owners and failure modes. Treating the chat window as all three gets messy fast.

How should a long-running agent recover?

Anthropic's November 26, 2025 long-running harness work uses an initializer to establish the environment, then coding sessions that make incremental progress and leave usable artifacts. It addresses a boring but expensive problem: a fresh session has to reconstruct what happened before it can safely continue.

A practical implementation should save the objective, current source revision, exact artifact, checks, external operation IDs and next action. Keep intent separate from observation. “Deploy requested” and “deployment verified” are different records. If a request times out, inspect the provider before sending it again. Otherwise your recovery loop can create the duplicate it was supposed to prevent.

Test that behavior deliberately. Stop a worker after an external system accepts a write, restart it with fresh context, and check whether it finds the existing result. Then repeat after the short-term context has disappeared. The recovery test should work from durable records, without someone remembering the missing step in Slack.

Do we need more agents or better evidence?

A September 30, 2026 preprint on autonomous ML engineering offers a useful reality check. Under matched time budgets and the same model backbone, its authors report that elaborate open-source harnesses did not outperform a minimal coding-agent baseline on the MLE benchmarks studied. That's a bounded result, not proof that enterprise controls are optional.

The decision rule I'd use: add orchestration when a measured failure demands it. Compare the simpler loop against the proposed multi-agent setup on your own tasks. Track correct completion, rework, review delay, recovery behavior and cost per accepted result. A dozen agents producing a dozen plausible explanations is still a review queue.

Which engineering roles own this work?

For an initial team, assign four responsibilities, even if people cover more than one. AI platform engineering owns the execution environment and tool boundaries. Context engineering owns retrievable product rules, architecture and source freshness. Evaluation engineering owns task-specific checks and regression cases. A delivery owner connects acceptance criteria to the release and its observed behavior.

Those are proposed responsibilities, not a universal new org chart. TeamStation's context engineer role page is a useful planning entry point when missing context is the bottleneck. Start with the failure you need someone to own, then choose the role. Renaming every developer “agent engineer” won't fix unclear accountability.

This also connects to distributed delivery. TeamStation's Distributed Engineering Operating Systems article discusses ownership, telemetry and governance across teams. The research library gives CTOs and CIOs related methods and their stated boundaries, while TeamStation services connects that planning to governed AI and nearshore engineering delivery.

Pick one real workflow this week. Give it a clear owner, a small completion test and a restart drill. Make the worker show the artifact and the observed result. Ship the loop once, inspect the failure points, then expand what it can do. That gives the next budget discussion something more useful than a demo.
