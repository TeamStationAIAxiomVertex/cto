Agentic AI SDLC: build a loop that survives a restart

The agent can write the PR. Let's give your team a way to prove what shipped and pick things back up when the session drops.

Lonnie McRoreyOctober 10, 2026For CTOs & CIOs

The quick take

  1. Keep the receipts. Save the work and what actually happened.
  2. Try a restart. Fresh context should still find the last result.
  3. Name an owner. Someone checks the release and calls it done.

An agentic AI SDLC needs a work loop that can recover: clear repo context, bounded tools, useful tests, durable records and someone who owns the release. For CTOs and CIOs, those belong in the same budget conversation. The harness is the software that connects those pieces around the agent.

You know that slick demo. The agent writes code, opens a PR and makes the whole thing look pretty easy. Then the session drops, a deploy times out or someone asks what actually shipped. That's where the engineering job gets interesting. Your team needs evidence it can pick up and use, even when the original chat is gone.

Which agent integration fits the job?

OpenAI's Codex platform guide, published August 19, 2026, gives platform teams a useful menu. Use codex exec for bounded background tasks, the SDK for programmatic sessions, and app-server for products that need ongoing threads, progress updates and approval UI.

Keep the choice practical. A CI job checking a PR has a different lifecycle from an internal app where a colleague resumes yesterday's work. Pick the interface that fits that workflow before adding another layer of orchestration.

Anthropic's Managed Agents architecture, published April 8, 2026, separates the session log, agent loop and execution sandbox. That gives each piece its own recovery path. A replacement harness can read the durable session and continue, while credentials can stay outside the sandbox. For a CIO, that's a useful ownership discussion: who runs the worker, who retains the history and who controls access?

How does the agent pick up where it left off?

Anthropic's long-running harness research, published November 26, 2025, starts with an initializer that prepares the environment. Later coding sessions make incremental progress and leave artifacts the next session can use.

You can borrow that pattern. Save the objective, source revision, exact artifact, check results, external operation IDs and next action. Record what you requested separately from what you observed. A deploy request and a verified live release each need their own entry.

Then try the awkward bit on purpose: stop the worker just after an external system accepts a write. Restart with fresh context. Can it find the accepted result before sending another request? Repeat after the short-term context is gone. That's a useful recovery drill, and it beats asking someone to remember the missing step over coffee.

When is more orchestration worth it?

A September 30, 2026 preprint on autonomous ML engineering adds a helpful reality check. With the same model backbone and matched time budgets, its authors found that elaborate open-source harnesses offered no advantage over a minimal coding-agent baseline on the MLE benchmarks they studied. The finding applies to those experiments; enterprise release controls still need their own evaluation.

Before buying more agent machinery, compare the simple loop and proposed setup on real tasks. Track correct completion, rework, review delay, restart recovery and cost per accepted result. Add orchestration where the evidence shows it helps. A dozen agents can still leave you with a dozen things to review. Yep, the queue survives the demo.

Who owns the loop?

Start with four responsibilities. AI platform engineering owns execution and tool boundaries. Context engineering owns retrievable rules, architecture and source freshness. Evaluation engineering owns task-specific checks and regressions. A delivery owner connects acceptance criteria to the actual release. One person can cover several responsibilities; make the ownership visible.

What should we test this week?

Use one low-risk workflow your team already understands. Say the agent drafts a documentation PR and CI checks it. Before the run, agree on the exact file change, the checks that matter and the person who accepts the result. Keep the first drill small enough that everyone can follow what happened.

  • Save: the task, commit, check results and PR ID in durable records.
  • Restart: end the worker's session, then start a fresh one from those records.
  • Reconcile: find the existing PR and observed CI result before trying another write.
  • Accept: have the release owner inspect the result and record the next action.

If the fresh worker needs someone to retell the story, you've found the next fix. That's useful progress. Give the context and recovery path some attention, run the drill again, and expand the workflow when the evidence supports it.

Pick one workflow this week. Give it an owner, a small completion test and a restart drill. Have the worker show the artifact and the observed result. Ship that loop, inspect where it gets messy, then expand. You'll have something concrete for the next CTO or CIO budget chat.
