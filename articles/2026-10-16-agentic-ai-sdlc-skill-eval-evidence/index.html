Agentic AI SDLC: what your skill eval should prove

A green agent skill eval needs a clear explanation of what passed. For CTOs and CIOs, I'd start with the task, the app and the evidence saved from the run. That's where a useful release decision begins. IMO, a score without that context leaves the next engineer doing detective work.

This companion focuses on the evidence to ask for before a skill joins your team's release workflow. The method is simple enough to use on one real PR, then expand when a failure shows you what's missing.

What belongs in the first skill test?

OpenAI's guide to testing agent skills separates outcome, process, style and efficiency checks. Those checks ask different questions, so keep their results visible instead of hiding everything behind one score.

For a repo maintenance skill, I'd write a small task with a clear expected change. I'd also test a dirty working tree and a nearby request that should leave files alone. Save the starting state, the diff, the test result and any unexpected action. If the skill edits a file during an explanation-only request, the engineer has a specific failure to reproduce.

Give the skill an owner and keep its version beside each result. A repair should run against the same test version as the earlier attempt. When the requirement changes, update the test deliberately and retain the earlier record, bc comparisons get messy when the pass condition moves quietly.

Why run the same task through the real app?

OpenAI and deepsense.ai's harness-aware plugin evaluation walkthrough compares direct tool tests, a standalone model loop and a product harness. The harness controls parts of the prompt and which tools the model can reach.

My practical take: use direct tool tests to find local failures quickly, then run representative tasks through the app your engineers actually use. Record the installed skill, model, available tools and permissions. A passing tool check doesn't tell you whether the app exposed that tool during the task.

This is a release risk for distributed engineering teams too. The engineer picking up the issue needs the same setup, a reproducible failure and a clear repair owner. A screenshot with no version or task details leaves too much guesswork.

What should the release owner inspect?

Anthropic's agent evaluation guide distinguishes the agent's recorded interaction from the final state of its environment. I'd use both when reviewing a change: confirm the requested behavior, then inspect the run for skipped checks or unintended edits.

Keep failed attempts in the record. They help the release owner discuss cost, review effort and delivery risk without pretending every task worked on the first try. Heads-up, this is a proposed review method, not a claim that a particular model or team has passed it.

For a useful ownership split, the skill owner handles instructions and examples, QA owns the expected outcomes, and platform engineering handles runtime connections. One engineer can cover several jobs. Just make sure a failure has a named destination.

Where does this fit in the wider workflow?

The main agentic AI SDLC skills article explains how evaluation methods, runtime checks and release ownership fit together. Use that framework to decide which evidence belongs in your next skill review.

If product rules or repo context keep getting lost, the context engineer role helps frame the ownership discussion. The agentic engineering concepts guide gives the team shared terms for that work. Bring one failing case and its owner to a discussion about TeamStation's engineering services, so the software quality conversation stays tied to a real task.

Start with one skill this week. Ask for its version, one representative task and the evidence from the actual app. Then review the first failure with the person who can fix that step.
